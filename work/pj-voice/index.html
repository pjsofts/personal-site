PJ Voice: an AI phone agent that books appointments without booking the wrong customer

Callers phone a number and talk to an agent that looks up their account, checks availability, and books, moves or cancels appointments. I designed it so that the mistakes that cost a business money are blocked in code, not left to the prompt.

Live project site ↗ Source code ↗ Tutorial ↗

The problem

Voice agents are easy to demo and hard to trust. A model that sounds right can still attach a booking to the wrong account, offer a slot that isn't free, or go silent when a dependency fails, and the caller hangs up. On the phone there's no screen to catch the mistake, and callers start hanging up after about a second of silence.

Key decisions and trade-offs

1. Correctness lives in the tool server, not the prompt

Prompts drift and models change. Anything that would cost the business money (a double booking, a wrong price, a booking on the wrong account) is enforced in code the model can't skip: offered-slot guards, ownership checks and idempotent writes. The prompt explains the rules; the server enforces them.

2. Hide IDs from the model

The worst tool error isn't an invalid argument, because validation catches those. It's a valid ID for the wrong customer. So a parameter marked as injected is removed from the schema the model sees and filled in by the server. If the model can't see the field, it can't fill it wrongly.

parameters:
  caller_phone: {type: string, x-injected: caller_phone}   # filled by the server, never by the model

Trade-off: when an injected value is missing, the call still goes out and the server answers with an actionable error ("no customer identified yet, call find_customer first"). Blocking the call would end the conversation; this lets the agent recover in the same turn.

3. Stage graphs instead of one giant prompt

A single prompt with every tool makes wrong tool choices more likely and every turn slower. The call is split into stages (triage → booking → manage), each with its own instructions and a small tool set. Handoffs are silent tool calls, and hop caps stop two stages bouncing the caller back and forth.

4. Never drop a call because a dependency failed

If this failsThe agent does this
Tenant config webhookUses the last known good config
Primary LLMSwitches to a fallback model
A tool times outApologises, offers a callback, and the call continues

5. Built for a one-second latency budget

Streaming speech-to-text, LLM and text-to-speech end to end, one HTTP hop per tool, short per-tool timeouts, a prewarmed voice-activity detector per worker, and no extra LLM calls in the turn path.

6. One engine for phone, text and tests

The voice worker and the text runner share the same config, stages, tools and guards. So the real logic runs in unit tests and evals without any audio, and SMS or chat come almost for free.

How I know it works

Unit tests can't catch a prompt change that makes the agent rude or forgetful, so PJ Voice tests whole conversations. An LLM plays the caller, the agent handles the call through the text runner, and weighted validators score the outcome: was the right tool called, did the backend end with the right number of appointments, did the agent say something it shouldn't.

pjvoice eval examples/demo-salon.yaml evals/scenarios --repeat 3 -v

What I'd do next

More eval scenarios for hard calls (interruptions, unclear dates, callers who change their mind twice), latency numbers per stage published alongside the evals, and a hosted demo number people can call.

Stack

Python 3.11+, LiveKit Agents, Pydantic, FastAPI, SQLite, plain HTTP tools, YAML configs, any OpenAI-compatible LLM. SIP or browser calls.
